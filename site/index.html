Why this exists

Prose doesn’t scale. Copies rot.

01 Drift

Every CLAUDE.md and AGENTS.md forks the day you paste it. Ten repos, ten slowly diverging rulebooks — and no way to tell which one is right.

02 No teeth

A convention written as prose is a suggestion. Agents skip it under pressure; humans skip it on Fridays. Nothing fails when it’s ignored, so it is.

03 Stale

Your team learns something hard-won in one repo. The other nine never hear about it. Best practice moves monthly; hand-syncing doesn’t.

Rule-sync tools move files. Claudinite moves enforcement, procedure, and scheduled work — as one versioned unit.

Mechanism 01

The pack

A pack is a convention that ships with its own means of survival. Not a document — a versioned unit with four layers, vendored into each consuming repo.

  • Rules are injected into every agent session, automatically.
  • Checks are executable — they fail the session or CI when work drifts, and the failure message carries the fix.
  • Skills load on demand, so procedure never bloats context.
  • Tasks run on the repo’s own scheduler, unattended.

Mechanism 02

The session loop

Hooks wire packs into Claude Code. Rules load at session start; checks run when the agent tries to stop. Drift is caught before it merges — and the finding is the instruction.

  • Blocking findings hold the session open until fixed.
  • Advisory findings surface without blocking.
  • The same sweep runs again in CI, so nothing slips past on a laptop.

Mechanism 03

No repo falls behind

Every consumer runs an hourly scheduler on its own repo-hashed minute — this site’s repo fires at :26 — and a nightly baselining task re-vendors the latest canon.

  • Updates arrive as ordinary PRs, gated by CI, auto-merged when green.
  • The canon is vendored — pinned, tracked, reviewable in your own history.
  • Sessions and CI read the same snapshot; there’s nothing to fetch and nothing to trust at runtime.

Mechanism 04

One repo pays.
Every repo learns.

Claudinite doesn’t just distribute conventions — it grows them. Lessons are mined from real work: merged sessions, issues, PRs. Keepers land in the repo’s local packs, get deduped against the canon, and the portable ones are promoted so the whole fleet inherits them.

    FAQ

    Fair questions

    What exactly gets added to my repo?

    A tracked, read-only vendored canon under .claudinite/shared/ (engine + packs), a pack declaration in .claudinite-checks.json, Claude Code hooks in .claude/settings.json, one thin scheduler workflow, and a conformance step in CI. All of it arrives as a single reviewable bootstrap PR.

    Will it fight my existing CLAUDE.md or AGENTS.md?

    No. Packs carry the layer those files can’t — enforcement, procedure, scheduled work — and Claudinite’s own advisory check nudges your root CLAUDE.md to stay lean and universally applicable, which is where community best practice already points.

    What happens when a check fails?

    At session stop, blocking findings hold the session open — each one states what drifted and how to fix it, so the agent fixes it then and there. The same sweep runs in CI on every PR, so a bypassed hook still can’t merge drift.

    Do I need a server or an account?

    No. Claudinite is files in your repo plus your existing GitHub Actions. There is no hosted service, nothing phones home, and leaving is deleting a directory and two hook entries.

    How do updates reach my repos?

    A nightly baselining task re-vendors the latest canon and opens a PR; CI runs; green PRs auto-merge (that’s configurable). Your fleet converges on the current canon without anyone hand-copying anything.

    Can it learn rules specific to my codebase?

    Yes — that’s the growth lifecycle. Lessons extracted from your merged sessions and PRs land in your repo’s local packs. Portable ones can be promoted into the shared canon; repo-specific ones stay local. Either way they graduate from prose toward checks.
